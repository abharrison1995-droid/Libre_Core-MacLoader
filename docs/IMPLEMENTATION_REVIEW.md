## Assessment

This is a detection/reporting/dependency foundation, not an installer or a working EFI generator. The existing v0.0.4 features need a repair/qualification tranche before v0.0.5. ## Additional improvements and qualifications

- `macloader/detection/linux.py:334` probes USB within network detection and again in `probe`; reuse one inventory to avoid duplicate reads and inconsistent hotplug observations. CPU parsing counts processor entries as both cores and threads. Include these in G0.4.
- `macloader/dependencies/cache.py:127` accounts for ZIPs only; `clear_cache` leaves orphan temporary files. Add resource accounting, retention and orphan cleanup in G0.6. Large stdout/stderr capture is a lower-priority probe resource concern.
- Fetching verified dependencies for a preliminary but otherwise eligible plan is not itself evidence of a defect: acquisition success and build readiness are different states. The interface must say which succeeded; an unresolved build must never become VALID or USB-ready. Blocked hardware remains rejected under G0.3.
- Raw probe output is currently deliberate and opt-in sanitization is documented. This review does not call all raw output a vulnerability. Before introducing automatically persisted/shareable build artifacts, ensure redaction by default at those boundaries and test free-text/nested evidence, error paths and identity handling (G2/G6).
- Python dependency lower bounds are normal package metadata, but a tested constraints/lock policy is needed for reproducible release qualification (G6). It need not force exact runtime pins on every library consumer.
- Existing resolved objects contain mutable catalog references, and tests mutate artifact hashes. Use isolated test catalogs and immutable release inputs so test execution or a later catalog change cannot alter an already accepted lock (G0.5).
- Ordinary pre-existing paths resolving outside the extraction root are already checked. Review suggestions about symlinks/races are hardening requirements for future extraction, not a reproduced blanket traversal bypass. Use a private staging/no-follow design and adversarial tests rather than claiming a proven current exploit.

### Post-closeout diff review (2026-09-08): 3 real bugs found and fixed, 7 tracked open

The spot-checks above verified R01–R16's specific claims, but did not amount to an independent line-by-line review of the full G0 diff. A follow-up 8-angle review (correctness, removed-behavior, cross-file, reuse, simplification, efficiency, altitude, conventions) of the complete uncommitted diff — including the new `contracts.py`/`recovery/`/`removable/` files — surfaced 10 findings. Three were genuine regressions in the exact mechanisms G0.2–G0.4 were meant to fix, and have been corrected in this working tree; the rest are tracked here, unfixed, out of scope for this pass.

**Fixed:**

| # | Finding | Fix |
|---|---|---|
| 1 | `macloader/compatibility/engine.py`'s "trust completeness" check used `inventory_status` keys (`ethernet`/`wifi`/`bluetooth`/`audio`/`input`) that neither `linux.py` nor `windows.py` actually emitted — and a separate unconditional `required_categories` loop skipped the completeness check entirely for audio/ethernet/wifi/storage. Net effect: any real machine with a legitimately empty category (e.g. a T480s, which has no onboard Ethernet) was always forced to UNKNOWN, defeating the exact capability-propagation fix G0.4 was supposed to deliver. | Both providers now emit `inventory_status` keys aligned to the engine's category names, with completeness meaning "the underlying source was queried successfully" (sysfs/PnP-query reachable) rather than "a device was found." `engine.py`'s `required_categories` loop was narrowed to only `cpu`/`graphics` (the two fields with no legitimate "confirmed empty" state); audio/ethernet/wifi/storage now go through the completeness-aware path exclusively. Verified with both a positive case (empty-but-confirmed-complete category → no longer UNKNOWN) and a negative control (empty and unconfirmed → still correctly UNKNOWN). |
| 2 | `generate_build_plan()` unconditionally appends a "deferred to v0.0.5" unresolved requirement whenever an iGPU is detected (true for virtually every real T480/T480s), so `build_ready` is always `False` and `EfiBuilder.build()` raised a bare "blocked" error with no explanation. | `BuildPlanError` now includes the actual `unresolved_requirements`/dependency reasons in its message. Note this does **not** make `build_ready` reachable pre-G1 — that block is intentional (the framebuffer/device-property policy genuinely isn't frozen yet) and correctly stays in place; the fix is that the failure is now legible instead of opaque. |
| 3 | `_match_storage()` had a hardcoded `comp.id == "standard-nvme"` fallback in Python — a component-ID special case reintroducing the "assume a known part for unidentified hardware" pattern G0.2 removed everywhere else. | Replaced with a declarative `kinds: [nvme, sata]` match_rule in `storage.yaml`, checked the same way `_match_input_component` already checks `kinds`. Behavior is unchanged and verified correct: an unbranded NVMe with no PCI info still matches `standard-nvme` (intentional — generic NVMe/AHCI genuinely works via macOS's native driver), PM981 still matches `samsung-pm981` first, and an unrecognized kind (e.g. eMMC) still correctly returns UNKNOWN. |

Full suite re-verified after all three fixes: **79/79 passing, mypy clean.**
